# Scheduled backup lifecycle

Optional config.json scheduled_backups owns an IANA timezone and stable named plans. The service validates and compiles enabled requests before binding HTTP or starting workers. Disabled plans still receive structural, Cron, compression and filter validation; their keys need not be present. Config changes require restart. The schedule parser uses croner's Chrono backend; chrono-tz supplies bundled IANA rules.

The scheduler checks UTC wall time once per second and matches only the current UTC minute converted to the configured timezone. It never scans elapsed minutes. Initialization advances persisted cursors to at least the startup minute, so startup and restart do not replay missed occurrences. Forward clock jumps and sleep skip elapsed minutes; backward jumps do not revisit minutes below the persisted high-water mark. Local times missing during daylight-saving transitions have no UTC occurrence; repeated local times can match twice, subject to the active-job guard.

Job schema v5 adds paired nullable schedule_id/scheduled_for columns and schedule_cursors(schedule_id, minute). Each minute, each enabled plan advances its cursor and conditionally inserts its request in one SQLite write transaction. Updating the cursor acquires the writer lock before checking queued/running jobs. A partial unique index additionally permits only one active task per schedule. Skipped busy occurrences still advance the cursor. Job notification occurs after commit. Minute values are UTC Unix minutes; scheduled_for exposes the same occurrence in Unix milliseconds.

Queued tasks contain a request snapshot and key fingerprint, so editing or disabling a plan does not change admitted tasks. Removing a plan does not cancel its tasks or delete its cursor/history. Retain a stable id for the same plan; use another id for independent work. Manual jobs have no schedule identity and remain independently admissible. Failed jobs do not block the next scheduled occurrence.

The scheduler and worker share the service stop signal. The scheduler stops admitting work before database closure, while existing worker shutdown semantics remain unchanged. A tick racing shutdown may commit a queued job; committed work is retained. Scheduler database/clock-matching errors and task panics terminate the service with diagnostics rather than leaving HTTP running without scheduling. At most one service instance may own a working directory. Job schema v4 is rejected without migration; the current repository schema is v6, independently of the scheduler.
