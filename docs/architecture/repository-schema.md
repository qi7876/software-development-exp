# Repository schema v4

The v4 model and SQL read/write bindings persist root and entry metadata,
symbolic link targets, and statistics in one transaction. Backup collects these
attributes before reading contents or descending into directories. Symbolic links
have no payload in the repository: their original target is stored only in SQLite.
Unsupported entry types are skipped and counted. Filtering uses strict directory pruning; rejected directory descendants are not traversed or counted.

Restore applies saved Unix metadata and recreates symbolic links without opening
their targets. Directory attributes are restored after children, followed by the
source root attributes on the destination root. Synchronization uses the already
opened directory handle so restrictive restored permissions do not prevent it.
Repositories are trusted and source trees must remain unchanged during backup.

Repository databases require `PRAGMA user_version = 4`; no migration is provided.
Use a new repository for v4 and a new working directory for job schema v3. No migration is provided; old data is not deleted. Job schema v3 distinguishes requests with pinned encryption settings from older request JSON.

## Storage contract

`backups` stores the header, source root metadata, and final statistics.
`entries` stores regular files, directories, and symbolic links. All metadata and
statistics columns are required, with no fabricated defaults.

| Columns | Representation |
| --- | --- |
| `format_version` | Must be 4 |
| `compression` | JSON `null`, `{"algorithm":"zstd","level":3}`, or `{"algorithm":"lz77","window_kib":64,"search_depth":32}` |
| `encryption` | `none` or `xchacha20poly1305-stream-be32-v2` |
| `encryption_key_id`, `encryption_key_fingerprint` | Both null without encryption; otherwise the stable key identifier and 64-digit SHA-256 fingerprint |
| `root_uid`, `root_gid`; entry `uid`, `gid` | Numeric IDs, 0 through 4294967295 |
| `root_mode`; entry `mode` | Permission and special bits only, 0 through 4095 (octal 07777), without file type bits |
| `root_atime_seconds`, `root_mtime_seconds`; entry `atime_seconds`, `mtime_seconds` | Signed Unix seconds |
| Corresponding `*_nanoseconds` | 0 through 999999999 |
| `entries_created` | Final entry count, excluding the source root |
| `skipped_unsupported`, `skipped_filtered` | Nonnegative, disjoint skip counts |
| `path` | JSON-serialized relative `PathBuf`, as in the existing storage convention |
| `link_target` | JSON-serialized original target `PathBuf`; do not resolve or normalize |

Each entry belongs to an existing backup; ordinals and paths are unique within a
backup. File entries require nonnegative `original_size` and a `checksum`, with
no `link_target`. Directory entries have none of these three fields. Symlink
entries require only `link_target` and have no payload file.

Restore validates relative entry paths and checks file sizes and checksums. This
iteration assumes trusted repositories generated by the application; it does not
promise safe restoration of adversarially edited metadata. SQL text uniqueness
does not establish path equivalence. Storage validates that `entries_created`
equals the number of inserted entries before committing the publication transaction. Root
metadata, entries, and counts must all be bound in that transaction.

## Verification and remaining work

Run `cargo test jobs::backup::tests` for traversal, content integrity, root and entry
metadata, metadata-only links (including dangling and cyclic links), unsupported
type statistics, empty sources, and atomic metadata publication. The full test suite
also exercises ordinary file/directory restore and HTTP lifecycle behavior.

Filter tests cover regex precedence, metadata fields, octal permissions, time
boundaries, invalid rules, strict directory pruning, and encountered-entry counts.
HTTP tests check that rules survive restart and affect restored contents, and that
invalid filter jobs fail before creating repository contents. The job request JSON
stores patterns, not compiled regular expressions; no task-table SQL change is needed.

The browser console provides optional filter controls and always submits the complete
filter object. Remaining work includes exposing stored backup statistics in job results.

The schema rejects old databases before querying their tables. It does not delete
or upgrade any existing database or backup contents.


## Content encoding and keys

Each backup chooses no compression, Zstd or LZ77, independently of encryption. Six modes may coexist in the same repository. Files retain their relative names; only their contents are encrypted. Sizes, checksums, Unix metadata, and link targets remain plaintext. The repository is still trusted metadata, not an encrypted catalog.

The payload format, authenticated framing, and key lifecycle are described in [content encryption](content-encryption.md). Restore automatically selects its decoding pipeline and requires the saved key identifier and fingerprint before creating restored entries. SHA-256 and size checks still cover original plaintext bytes.
